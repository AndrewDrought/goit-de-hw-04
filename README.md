# goit-de-hw-04

Дослідження Spark Jobs, лінивого виконання та кешування DataFrame у PySpark.

## Результати

Три незалежні запуски дали очікувані **5, 8 і 7 завершених Jobs**.

| Частина | Програма | Читання CSV | Перший collect | Другий collect | Разом |
| --- | --- | ---: | ---: | ---: | ---: |

| 2 | [part2.py](part2.py) | 2 | 3 | 3 | **8** |

## Запуск

Перевірене середовище: Linux, Python 3.12, Java 17, PySpark 3.5.3. Параметри: `local[*]`, `spark.sql.shuffle.partitions=2`, `spark.sql.adaptive.enabled=true` (типове значення для цієї версії).

1. Встановлення залежностей:

   ```bash
   python -m pip install -r requirements.txt
   ```

2. Датасет [nuek-vuh3.csv](https://drive.google.com/file/d/1XmmUpuTwNH6YZHZMVRYQe0vJvBy3vQY5/view) із 1 000 записів має бути в корені проєкту поруч зі скриптами. CSV не включено до репозиторію.

3. Із кореня проєкту запустити програми **по черзі**, завершуючи попередню перед наступною:

   ```bash
   python part1.py
   python part2.py
   python part3.py
   ```

   Кожна програма очікує Enter після обчислень. Під час очікування доступна сторінка [Spark UI → Jobs](http://localhost:4040/jobs/). Enter звільняє ресурси та закриває сесію; у частині 3 перед цим виконується `unpersist()`.

У середовищі перевірки для прив’язки Spark до локального інтерфейсу задано `SPARK_LOCAL_IP=127.0.0.1`. Якщо локально виникає `Cannot assign requested address`, у Bash можна виконати `export SPARK_LOCAL_IP=127.0.0.1` перед запуском, а в PowerShell — `$env:SPARK_LOCAL_IP="127.0.0.1"`.

## Пояснення кількості Jobs

У всіх частинах **Jobs 0–1** з’являються під час завантаження CSV: отримання першого рядка для заголовка та проходу для `inferSchema`.

**Частина 1 — 5 Jobs.** Дія `collect()` створює ще три Jobs (2–4). За увімкненого AQE окремо матеріалізуються shuffle для `repartition(2)` і `groupBy("unit_id")`, після чого виконується фінальна агрегація, фільтрація `count > 2` та повернення результату. Сам `where()` не запускає Job.

**Частина 2 — 8 Jobs.** Перший `collect()` запускає Jobs 2–4, другий — Jobs 5–7. Повернення списку рядків драйверу не кешує DataFrame. У цьому плані другий action повторює читання даних, repartition та агрегацію, тому додаються три Jobs.

**Частина 3 — 7 Jobs.** Перший `collect()` створює чотири Jobs: два для shuffle (2–3), один для матеріалізації агрегованого результату в кеші (4) і один для повернення кешованих рядків драйверу (5). Другий `collect()` створює лише Job 6: читає кеш через `InMemoryTableScan`, фільтрує та повертає результат без нових shuffle. Економія двох Jobs на повторній дії мінус один додатковий Job матеріалізації дає зменшення з 8 до 7.

`skipped` біля залежних stages означає, що їхні вже готові результати повторно використано; це не помилка. Jobs, stages і tasks — різні одиниці виконання. Числа 5/8/7 описують ці конкретні плани та налаштування, а не універсальну відповідність між actions і Jobs.

## Що робить cache()

- `cache()` позначає DataFrame для збереження; обчислення та заповнення кешу відбуваються під час першої дії.
- Наступні дії можуть повторно використовувати збережений проміжний результат замість повторного виконання його плану.
- Для **DataFrame у PySpark 3.5.3** типовий рівень — **`MEMORY_AND_DISK_DESER`**, тобто пам’ять із можливістю зберігання блоків на диску. `MEMORY_ONLY`, згаданий в умові, не є типовим рівнем цього API.
- У перевіреному запуску збережено 2 із 2 партицій: **1 296 байтів у пам’яті, 0 байтів на диску**.
- `unpersist()` звільняє кешовані блоки. Кешування корисне для повторного використання дорогих обчислень, але має власні витрати й не завжди прискорює одноразовий запит.

`groupBy().count()` тут є трансформацією, що створює агрегований DataFrame. На відміну від нього, `DataFrame.count()` без групування є action.
